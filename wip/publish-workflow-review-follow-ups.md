# Publish workflow — review follow-ups

Findings from the agent review of PR #61 (`release/v0.7.1`) that were not fixed in the round they were raised. These are work-in-progress notes, deliberately not release-facing.

## The build backend is unpinned, so reproducibility is only conditionally guaranteed — *closed*

- **Raised by:** Greptile, P2, on [PR #61](https://github.com/Pipelex/kajson/pull/61), thread anchored at `.github/workflows/publish-pypi.yml:163-170` — *"Reruns replace published artifacts … Without a reproducible-build guarantee, this can give the same version different hashes across PyPI and GitHub."* Re-raised in round 2 by a local `cubic review --base main`, anchored at the `overwrite: true` the round-1 fix had added.
- **Verdict at the time:** the substantive half (a *different commit* replacing a tagged release's assets) was a duplicate of the Codex/cubic P1 and was fixed by gating `skip-existing` on `github.run_attempt > 1`. The reproducibility half was rejected as a false positive: kajson builds with hatchling, whose `reproducible` build option defaults to `true` and uses a fixed default timestamp when `SOURCE_DATE_EPOCH` is unset, so rebuilding the same commit yields byte-identical artifacts.
- **The residual:** that rejection rested on hatchling's behaviour, and `pyproject.toml` `[build-system] requires = ["hatchling"]` names no version. A hatchling release landing between run attempt 1 and a later recovery re-run could change the bytes, and the GitHub Release assets — along with the Sigstore bundles attesting them — would then diverge from PyPI's immutable originals for the same version.
- **Why it was deferred at first:** the window is narrow (a recovery re-run of an already-published version, spanning a hatchling release), nothing installs from the GitHub assets, and pinning a build backend is a separate call about how this repo wants its builds bounded — not a fix to make inside a release PR.
- **How it was closed:** neither of the two options originally sketched (pin `hatchling==<version>`, or set `SOURCE_DATE_EPOCH` from the commit timestamp). Both only make a *rebuild* reproducible, and only as far as the pin reaches — pinning hatchling does not pin hatchling's own dependencies, and `setup-python`'s `3.x` is free to move too. The `build` job now asks the artifacts API whether an earlier attempt of the same run already stored `python-package-distributions`, and reuses it instead of building again; `overwrite: true` is gone, since there is no longer a second build to overwrite the first with. That removes the whole class of divergence rather than the hatchling instance of it, and leaves the release path with one build per published version by construction.
- **Deliberate edges of that guard:** the check keys on the artifact existing, not on `github.run_attempt`, so a re-run of an attempt that died *inside* the `build` job still builds. An artifact that exists but has expired (past the retention window) fails the job with an explicit error rather than rebuilding, because at that point the run can no longer reproduce what it published and the right move is a new version.

## `github.run_attempt > 1` does not prove the re-run is a recovery — *closed*

- **Raised by:** Codex, P1, on [PR #61](https://github.com/Pipelex/kajson/pull/61), round 2, anchored at the `skip-existing` condition the round-1 fix introduced — *"it distinguishes attempts, but not a legitimate post-publication recovery from a rerun of the duplicate-version failure."*
- **Why it was accepted in round 2:** the round-2 bar is a comment clearly broken by the round-1 changes, and this is one — the gate is the round-1 fix. An unbumped push to `main` fails at PyPI on attempt 1 exactly as designed, but an operator re-running the failed jobs lands on attempt 2, where the gate opens `skip-existing`, the duplicate rejection becomes success, and `github-release` clobbers the tagged release's dists with the newer commit's build. The artifact-reuse guard above does not help: the artifact attempt 1 stored is that same newer commit's build. Admin pushes to `main` do happen in this repo, so the entry condition is not hypothetical.
- **How it was closed:** by guarding the step that does the damage rather than the one that lets it through. `github-release` now resolves `v$VERSION` through the commits endpoint before it creates, edits or uploads anything, and fails if the tag exists and names a commit other than `$GITHUB_SHA`. A tag that does not exist is allowed through, because that is what an attempt which died between the PyPI upload and `gh release create` looks like, and blocking it would break the recovery this whole fallback exists to enable. `skip-existing` keeps its attempt gate: it still stops the unbumped first attempt earlier and with a clearer error.
- **One trap worth recording:** `gh api` writes its *error* body to stdout, not stderr, so `$(gh api … 2>/dev/null || true)` yields the 422 JSON rather than an empty string for a tag that does not exist — which would have inverted the guard and failed precisely the recovery path. The result is checked against `^[0-9a-f]{40}$` before it is compared.
