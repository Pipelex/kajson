# Publish workflow — review follow-ups

Findings from the agent review of PR #61 (`release/v0.7.1`) that were not fixed in the round they were raised. These are work-in-progress notes, deliberately not release-facing.

## The build backend is unpinned, so reproducibility is only conditionally guaranteed — *closed*

- **Raised by:** Greptile, P2, on [PR #61](https://github.com/Pipelex/kajson/pull/61), thread anchored at `.github/workflows/publish-pypi.yml:163-170` — *"Reruns replace published artifacts … Without a reproducible-build guarantee, this can give the same version different hashes across PyPI and GitHub."* Re-raised in round 2 by a local `cubic review --base main`, anchored at the `overwrite: true` the round-1 fix had added.
- **Verdict at the time:** the substantive half (a *different commit* replacing a tagged release's assets) was a duplicate of the Codex/cubic P1 and was fixed by gating `skip-existing` on `github.run_attempt > 1`. The reproducibility half was rejected as a false positive: kajson builds with hatchling, whose `reproducible` build option defaults to `true` and uses a fixed default timestamp when `SOURCE_DATE_EPOCH` is unset, so rebuilding the same commit yields byte-identical artifacts.
- **The residual:** that rejection rested on hatchling's behaviour, and `pyproject.toml` `[build-system] requires = ["hatchling"]` names no version. A hatchling release landing between run attempt 1 and a later recovery re-run could change the bytes, and the GitHub Release assets — along with the Sigstore bundles attesting them — would then diverge from PyPI's immutable originals for the same version.
- **Why it was deferred at first:** the window is narrow (a recovery re-run of an already-published version, spanning a hatchling release), nothing installs from the GitHub assets, and pinning a build backend is a separate call about how this repo wants its builds bounded — not a fix to make inside a release PR.
- **How it was closed:** neither of the two options originally sketched (pin `hatchling==<version>`, or set `SOURCE_DATE_EPOCH` from the commit timestamp). Both only make a *rebuild* reproducible, and only as far as the pin reaches — pinning hatchling does not pin hatchling's own dependencies, and `setup-python`'s `3.x` is free to move too. The `build` job now asks the artifacts API whether an earlier attempt of the same run already stored `python-package-distributions`, and reuses it instead of building again; `overwrite: true` is gone, since there is no longer a second build to overwrite the first with. That removes the whole class of divergence rather than the hatchling instance of it, and leaves the release path with one build per published version by construction.
- **Deliberate edges of that guard:** the check keys on the artifact existing, not on `github.run_attempt`, so a re-run of an attempt that died *inside* the `build` job still builds. An artifact that exists but has expired (past the retention window) fails the job with an explicit error rather than rebuilding, because at that point the run can no longer reproduce what it published and the right move is a new version.

## `github.run_attempt > 1` does not prove the re-run is a recovery — *closed*

- **Raised by:** Codex, P1, on [PR #61](https://github.com/Pipelex/kajson/pull/61), round 2, anchored at the `skip-existing` condition the round-1 fix introduced — *"it distinguishes attempts, but not a legitimate post-publication recovery from a rerun of the duplicate-version failure."*
- **Why it was accepted in round 2:** the round-2 bar is a comment clearly broken by the round-1 changes, and this is one — the gate is the round-1 fix. An unbumped push to `main` fails at PyPI on attempt 1 exactly as designed, but an operator re-running the failed jobs lands on attempt 2, where the gate opens `skip-existing`, the duplicate rejection becomes success, and `github-release` clobbers the tagged release's dists with the newer commit's build. The artifact-reuse guard above does not help: the artifact attempt 1 stored is that same newer commit's build. Admin pushes to `main` do happen in this repo, so the entry condition is not hypothetical.
- **How it was closed:** by guarding the step that does the damage rather than the one that lets it through. `github-release` now resolves `v$VERSION` through the commits endpoint before it creates, edits or uploads anything, and fails if the tag exists and names a commit other than `$GITHUB_SHA`. A tag that does not exist is allowed through, because that is what an attempt which died between the PyPI upload and `gh release create` looks like, and blocking it would break the recovery this whole fallback exists to enable. `skip-existing` keeps its attempt gate: it still stops the unbumped first attempt earlier and with a clearer error.
- **One trap worth recording:** `gh api` writes its *error* body to stdout, not stderr, so `$(gh api … 2>/dev/null || true)` yields the 422 JSON rather than an empty string for a tag that does not exist — which would have inverted the guard and failed precisely the recovery path. The result is checked against `^[0-9a-f]{40}$` before it is compared.

## The tag guard failed open when the GitHub API could not answer — *closed*

- **Raised by:** a local `cubic review --base origin/main` in round 3, P1, anchored at the `TAGGED_SHA` capture the round-2 fix introduced — *"The command suppresses every API failure and treats any non-SHA response as a missing tag, including transient outages, rate limits, and authorization errors."* No PR bot reported it, so this note and the round-3 stamp are its only record.
- **Why it was accepted despite the round-3 bar:** round 3 normally changes nothing, and this was an explicit exception. The guard exists to refuse; a guard that reads "I could not find out" as "nothing to refuse" disarms itself precisely when it is least able to tell what it is letting through, and failing closed cost four lines that replace the old shape check rather than adding a branch beside it.
- **What the old code did:** `TAGGED_SHA=$(gh api "repos/$GITHUB_REPOSITORY/commits/v$VERSION" --jq '.sha' 2>/dev/null || true)` followed by a `^[0-9a-f]{40}$` test that blanked anything else. Measured against this repo, every failure mode produces a non-SHA body on stdout and is therefore indistinguishable: a missing tag is `{"message":"No commit found for SHA: v99.99.99",…,"status":"422"}` (exit 1), bad credentials are `{"message":"Bad credentials",…,"status":"401"}` (exit 1), and a transport failure is an empty stdout (exit 1). Only the first should open the recovery path.
- **How it was closed:** branch on `gh api`'s exit status first, and when it fails, on the error body's `.status`. `404` and `422` mean the tag genuinely does not exist and the recovery path proceeds; anything else — 5xx, a rate limit, a revoked token, or an empty body — fails the job with the API's own message. The `^[0-9a-f]{40}$` test is gone, because the exit code now does that job properly and keeping both would guard a state the success path cannot produce.
- **One trap worth recording:** `jq -r '.message // "fallback"'` does *not* supply the fallback for an empty body — `jq` on empty input emits nothing at all rather than `null`, so the alternative operator never runs and the message renders with a hole in it. The default is applied by the shell (`${REASON:-…}`) instead. The same shape is why `.status // empty` on an empty body correctly falls through to the hard-fail branch.
- **Verified before landing** by extracting the step's script from the YAML and running it against captured bodies with a stubbed `gh`: tag naming this commit passes, tag naming another commit refuses, `422` opens the recovery path, and `401` / `500` / empty-body all stop the job.

## The tagless recovery path is still allowed on trust — *open*

- **Raised by:** Codex and Greptile independently, both P1, round 3, on [PR #61](https://github.com/Pipelex/kajson/pull/61) at `.github/workflows/publish-pypi.yml:155-158`. Greptile: *"When commit A publishes a version to PyPI but fails before creating its tag, rerunning an unbumped commit B clears `TAGGED_SHA` and skips the mismatch check."* Codex asked for the same thing constructively — *"record that attempt 1 successfully published this run's artifact, or compare the artifact against PyPI, before allowing the tagless recovery path."*
- **The finding is real, but neither description is quite right about the code.** Nothing is silently cleared: the allowance is deliberate and documented in the step's own comment — absent means attempt 1 died between the PyPI upload and `gh release create`, which is the recovery this whole fallback exists to enable, and refusing it would break the feature. What the reviewers actually found is that the tag is a *proxy* for "did this run publish these bytes", and the proxy has a hole.
- **What it takes to reach it:** a transient failure in the window between the PyPI upload and `gh release create` — a window this PR itself shrank by moving release creation ahead of Sigstore, so the one failure that actually happened no longer costs the tag — *and* an unbumped commit reaching `main`, which is possible because `version-check.yml` runs on `pull_request` only and is not a required status check while the ruleset carries a bypass team, *and* an operator answering PyPI's unambiguous "file already exists" error by re-running the run instead of bumping the version.
- **Why it was deferred:** the round-3 bar is to change nothing and merge, and this cleared none of the exceptions. Merging exercises none of it — `v0.7.1` is neither tagged nor on PyPI, so the publish run is a clean first attempt with no prior artifact and no tag. If it were ever reached, the damage is GitHub release assets and Sigstore bundles disagreeing with PyPI for one version; nothing in this repo installs from those assets, and it is repairable with a `--clobber` of the correct files.
- **The fix, when someone picks this up:** stop inferring from the tag and check the invariant that actually matters — that the bytes about to be attached and signed are the bytes PyPI already holds. After the dists are downloaded in `github-release`, compare their digests against the published ones:

  ```bash
  PYPI=$(curl -fsSL "https://pypi.org/pypi/kajson/$VERSION/json" \
         | jq -r '.urls[] | "\(.digests.sha256)  \(.filename)"' | sort)
  LOCAL=$(cd dist && sha256sum *.whl *.tar.gz | sort)
  [ "$PYPI" = "$LOCAL" ] || { echo "::error::…"; exit 1; }
  ```

  The API shape is confirmed: `https://pypi.org/pypi/kajson/0.7.0/json` exposes `.urls[].digests.sha256` for exactly the wheel and the sdist, in the `digest  filename` layout `sha256sum` emits. This subsumes both the tag guard and the hatchling-reproducibility worry recorded at the top of this file, since it verifies bytes rather than provenance.
- **The open question, which is why this is not a mechanical follow-up:** the comparison makes a pypi.org outage fail the release job. That is the right default for a supply-chain guard and the wrong one for a release path that has already published, and choosing between them — hard fail, or warn and continue when PyPI is unreachable — is a maintainer's call, not a review round's.

## `gh release create` does not pin the tag to the commit being built — *open*

- **Raised by:** nobody. Found while verifying the two findings above, in code this PR did not touch.
- **The defect:** `gh release create "v$VERSION"` at `.github/workflows/publish-pypi.yml` passes no `--target`, so GitHub creates the tag at the default branch's current HEAD rather than at `$GITHUB_SHA`. On the legitimate recovery path — re-running a run after anything else has landed on `main` — the tag therefore names a commit that never built the release.
- **Why it matters more than it looks:** it quietly undermines the guard added in round 2. That guard trusts the tag to name the commit that shipped a version, and this is the line that can make the tag lie.
- **Pre-existing, not introduced here:** `origin/main` has the same omission, so it is outside this PR's scope and was not fixed under the round-3 bar.
- **The fix is one flag:** `--target "$GITHUB_SHA"` on the `gh release create` call. Worth doing together with the digest comparison above, since both concern the same question of which commit a release actually represents.
